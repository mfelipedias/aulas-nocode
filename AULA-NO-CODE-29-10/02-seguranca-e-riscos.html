Esconder na tela não é proteger

No no-code, a plataforma cuida da infraestrutura, mas a configuração do app continua sendo sua. A maioria dos incidentes vem de erro de configuração, não de falha da plataforma.

Sem privacy rule

Maria vê só as notas dela, porque a tela filtra. João pula a tela, chama a API e recebe as notas de todos.

Com privacy rule

Maria continua vendo as notas dela. João, pelo atalho, recebe uma lista vazia: a proteção está no banco, não na tela.

Regras de acesso mal configuradaso erro mais comum

O que aconteceSem privacy rules (Bubble) ou com RLS desligada (Supabase, usado pelo Lovable), qualquer pessoa consulta a API e recebe os dados. Validar só no front-end não protege. No IDOR, o usuário troca o ID na URL e abre o dado de outra pessoa.

O que fazerComece fechando tudo e abra só o necessário. Aplique o menor privilégio por perfil. Teste com usuários de perfis diferentes, inclusive visitante.

Segredos expostoschaves e tokens no lugar errado

O que aconteceEm apps gerados por IA, é comum a chave de API ir parar no código do navegador, que qualquer pessoa pode ler. Tokens colados em prompts, planilhas ou chats também vazam.

O que fazerGuarde credenciais no cofre da própria ferramenta (Make e n8n têm gerenciamento de conexões). Troque chaves que possam ter vazado.

Código gerado por IAfunciona não quer dizer seguro

O que aconteceLovable e similares geram código funcional, mas com autenticação frágil, validação ausente ou RLS incompleta.

O que fazerRevise o que foi gerado antes de publicar, principalmente login, pagamentos e acesso a dados.

Integrações e automaçõesMake, n8n, webhooks

O que aconteceWebhook público sem autenticação pode ser disparado por qualquer pessoa que descubra a URL. Conexões com permissão total ampliam o estrago. Cada app conectado é mais um ponto de vazamento.

O que fazerProteja o webhook com token ou validação de origem. Use o mínimo de escopo. No n8n self-hosted, cuide de atualizações, firewall, HTTPS e backups.

Dados pessoais e LGPDvocê responde pelos dados

O que aconteceQuem constrói o app é controlador ou operador dos dados, mesmo usando plataforma de terceiros. Dados sensíveis e de menores exigem cuidado redobrado.

O que fazerColete só o necessário, tenha base legal e política de privacidade, confira onde os dados ficam hospedados e prepare-se para pedidos de acesso, correção e exclusão.

Dependência do fornecedorpreço, queda, encerramento

O que aconteceSe a plataforma mudar preços, sair do ar ou encerrar, o app pode ser perdido. No Bubble, o código não é exportável.

O que fazerFaça backup periódico dos dados, documente a lógica do app e verifique SLA, histórico de incidentes e certificações (SOC 2, ISO 27001).

Contas e governançaquem entra no editor

O que aconteceA conta da plataforma controla todo o app. Contas compartilhadas e apps sem dono criam uma TI paralela (shadow IT).

O que fazerAtive autenticação em dois fatores, evite contas compartilhadas, revise acessos e separe teste de produção usando dados fictícios nos testes.

Plugins de terceirosmarketplace

O que acontecePlugins podem ter falhas ou coletar dados do seu app.

O que fazerPrefira os bem avaliados, mantidos e com muitos usuários, e revise as permissões que pedem.

Exemplo no Bubble: formulário de inscrição

Cenário: qualquer pessoa preenche o formulário (tipo de dado Inscricao, com nome, e-mail, telefone, ideia e trilha), mas só você, como admin, pode ver as inscrições.

  1. Em Data → Data types → User, crie o campo admin (sim/não). Marque sim só no seu usuário.
  2. Em Data → Privacy → Inscricao, crie a regra Admin com a condição Current User's admin is yes.
  3. Na regra padrão Everyone else, desmarque tudo. Sem isso, a regra de admin não protege nada.
  4. Teste com Run as: como visitante, a lista vem vazia; como admin, aparece tudo. O painel App data não serve de teste, pois mostra tudo ao dono.

Cuidado com a coluna Constraint

Em campos sensíveis como e-mail e telefone, deixe Constraint desmarcado para todos, menos para o admin. Com ele liberado, alguém pode descobrir valores por tentativa, buscando por exemplo e-mails que contenham um trecho.

E o webhook do Make continua funcionando?

Na maioria dos casos, sim. O que importa é de que lado está a integração e de onde saem os dados.

DireçãoPrivacy rules afetam?O que verificar
Bubble envia ao Make com os valores dos inputs do formulárioNãoNada, é o jeito mais seguro.
Bubble envia ao Make lendo os dados do banco, como visitanteSimCampos podem chegar vazios. Use os inputs ou um backend workflow.
Make lê o Bubble com token de adminNãoIgnora as regras. Proteja bem o token.
Make lê o Bubble com token de usuárioSimO usuário do token precisa ter permissão.

Teste de dois minutos

Ative as regras, saia da conta, envie uma inscrição de teste e abra a execução no Make. Se algum campo veio em branco, a causa é a regra de privacidade.

Com tudo fechado, como eu vejo os dados?

Regras de privacidade definem quem consegue ver. Para você consultar, escolha uma das opções.

SituaçãoMelhor opção
Só você consulta, de vez em quandoPainel App data do editor, com exportação em CSV. Não exige login nem tela.
Outras pessoas da equipe precisam verPágina admin com login e um Repeating Group de Inscricao, ou planilha compartilhada alimentada pelo Make.
Quer filtros, busca e botões no sistemaPágina admin com login e Repeating Group. A página redireciona quem não é admin, mas quem protege o dado é a privacy rule.

Exercício para a aula

  1. Crie duas contas de teste, Maria e João.
  2. Com a Maria, crie algumas notas.
  3. Entre como João e tente ver as notas da Maria: pela tela, mudando a URL e com o modo Run as do editor.
  4. Compare o resultado com a privacy rule desligada e ligada.

A proteção precisa estar no banco de dados.
